# Madeira's FEX patches

Changes to FEX that Madeira needs and that live in this repository, not in
the FEX submodule's repository. `apply.sh` applies them, in file-name order,
to the FEX working tree before `build/fex-arm64ec/build.sh` and
`build/fex-wow64/build.sh` build `xtajit64.dll` and `xtajit.dll`; it skips a
patch that is already applied, and `apply.sh --revert` takes them out. The
FEX submodule pin does not change.

These patches are for Madeira only and are not to be sent to FEX-Emu.

| Patch | What it fixes |
|---|---|
| `0001-windows-ios-smc-traps-per-16k-host-page.patch` | Self-modifying-code write traps per 16 KB iOS host page, both modules (The Escapists 2, Project Zomboid) |
| `0002-single-block-invalidation.patch` | Single-block invalidation under `SMCChecks=full`, ported from the DroidDeck FH6 build: `InvalidateCodeBuffersBlock` / `InvalidateThreadCachedBlock` / `InvalidateGuestBlock`, and `InvalidateUntrackedRange` for a block whose page bookkeeping is missing |
| `0003-exittox64-resolve-import-thunks.patch` | `ExitToX64` resolves an x64 import thunk — bare `ff 25 rel32` or hotpatched (prologue + `ff 25`, see `build/wine-patches/0001`) — through its IAT slot before its FFS tests. Without it a call that arrives here with `x9` = an import thunk takes `ios_ffs_no_bypass` and enters the JIT with `x9` still the thunk. EC targets now branch natively; genuine x64 ones fall through to emulation with `x9` restored, which is the correct x64 behaviour (the first case seen was `TlsAlloc` from ucrtbase's exit thunk) |
| `0004-exittox64-branch-native-for-ec-targets.patch` | `ios_ec_entry`: when `x9` matches no thunk shape it is a raw ARM64EC target, so canonicalise it into pool space and branch to it natively if `EcCodeBitMap` says EC, instead of entering the JIT with an all-zero CPU area (no `CpuStateFrame` yet during the DllMain walk) and branching to NULL |
| `0005-exittox64-follow-slot-fastforward.patch` | `ios_thunk_slot` follows a hotpatched thunk's IAT slot through a hybrid export's 14-byte x64 fast-forward stub (`48 8b c4 … 55 5d e9 rel32`, the shape `build/tools/ec-ffs-pad.py` preserves) and canonicalises both the slot value and each stub target from PE VAs into pool space before the `EcCodeBitMap` test — up to four hops, because kernel32 → kernelbase forwarders can chain. `arm64ec_iat_is_exported_x64` deliberately keeps those stubs x64-visible in `.hexpthk`, so without this the slot value is x64 byte space, fails the bitmap test, and reaches emulation (the 2026-11-14 `c0000005` at `pc=0`, `lr=ucrtbase+0x90f1c`). The original slot value is restored on every miss, so a miss behaves exactly as before. It also gives `ios_thunk_slot` a real 32-byte frame: the baseline pushed nothing while `ios_thunk_reject` branched into `ios_ffs_reject`, whose `ldp x4, x9, [sp], #16` pairs with `ios_ffs_check`'s push — so every correctly-rejected thunk popped 16 bytes that were never pushed. `x4` (x64 `R10`), which the bitmap test uses as scratch, is now saved and restored so `R10` reaches the callee intact; `x5` is deliberately untouched because `x4`/`x5` carry the ARM64EC variadic descriptor |
| `0006-report-unresolved-import-slots.patch` | Diagnostics: `IosFfsBypassLog` grows to 12 slots. `[6]`/`[7]` count import slots the fast-forward walk could not resolve and record the last such value; `[8]`/`[9]` count FFS prologues actually followed and record the last native target reached (`[ffs-follow]`); `[10]` keeps the unresolved slot value across `[7]` overwrites. A run with `followed=0` plus an `[ffs-slot]` value means the slot never held an FFS at all, which distinguishes a broken unwrap from a wrong diagnosis |

| `0007-exittox64-read-pool-slot-from-pe-view.patch` | Derive `ExitToX64`'s import slot from the **PE copy** of the thunk and read the slot's **value** there too. The `jmp rel32` a hotpatched import thunk carries is a *link-time constant*, so the file's copy is authoritative; the pool copy has been measured to hold a different one. The PE view is also the copy `loader.c` binds: it writes `n->n = …` with `n = get_rva(module, descr->FirstThunk)`, straight into the module's own IAT. Reading the *value* from the pool was the build-29 bug: a plain IAT slot is not carried over, so rva `0x50650` still held the file's unbound `0x63fc8` hint/name rva — not NULL, not `0xcc`, small enough to pass the EC bitmap's range check, so it was rejected into emulation and hit `enter_jit`'s br-to-NULL. Values below `0x100000` are now treated as unbound as well (PE images sit near `0x71fe…`, the pool near `0x15…`, the FEX arena at `0x7c00000000`), and the pool-derived slot plus the filler/NULL PE re-read remain as fallbacks. `IOS_POOL_TO_PE_TO` is the inverse of `IOS_PE_TO_POOL_TO` over `IosAliasEntries`; `IosFfsBypassLog[11]` counts PE-view re-reads. **Verified against `app/Madeira/arm64ec-windows/kernel32.dll` on 2026-11-14:** `x9` is `kernel32+0x35a70` = `48 8d a4 24 00 00 00 00 ff 25 d2 ab 01 00`; the file's `rel32` `0x1abd2` lands on rva `0x50650`, which the import directory confirms is `kernelbase.dll!GetCommandLineA`'s IAT slot (it holds `0x63fc8`, the hint/name record `0x155 "GetCommandLine"`, and carries no relocation — i.e. a normal unbound IAT entry). Re-verified 2026-11-15 against the same file: the bytes at rva `0x35a70` are `48 8d a4 24 00 00 00 00 ff 25 d2 ab 01 00`, so `rel32` is `0x1abd2` and `0x35a70 + 14 + 0x1abd2` is `0x50650`; the import directory puts that at index 202 of kernel32's kernelbase DLL import list (IAT starts at `0x50000`, `(0x50650 - 0x50000) / 8 = 202`) whose import name is exactly `GetCommandLineA`, and the file's slot value there is `0x63fc8`. The pool copy's `rel32` is `0x11402`, landing on rva `0x46e80`: past `.hexpthk` (va `0x40000` + vs `0x1cc0` = `0x41cc0`) and before `.rdata` (`0x50000`), so it reads the uninitialised gap, which is `0xcc` filler. Build 28's log shows exactly that (`x9-probe: thunk -> slot 0x153a96e80 = 0xcccccccccccccccc`, and `0x153a96e80 - 0x153a50000 = 0x46e80`) |

| `0008-exittox64-canonicalise-slot-target.patch` | Two changes to the same region. (a) Canonicalise `ExitToX64`'s resolved import target into POOL space *before* the `EcCodeBitMap` test: 0007 reads the slot's value from the PE view, and a bound ARM64EC target there can be stored as a PE address (`0x71fe…`), while the bitmap is indexed by `addr >> 15` and rejects anything at or above `0x40000` words — correct only for pool addresses (`0x15…`), so a slot that resolved *correctly* still failed the range check and went to emulation. `IOS_PE_TO_POOL_TO` is a no-op on a pool address and leaves the register untouched on an alias miss, so the plain pool path is unaffected. `IosFfsBypassLog[18]`/`[19]` record the target on either side of the conversion. (b) Move the counter dump from `ResetToConsistentStateImpl` to the exported `ResetToConsistentState`. Impl is only reached when the thread has FEX state, and the fault the dump exists to explain is exactly the one where it does not: the null-`ThreadState` bail returns `STATUS_SUCCESS` first, so ml1215–ml1218's dump never ran in any session — which is why `[ffs-log]` never appeared in a log despite the write path being sound. **Verified against the 2026-11-15 00:17:56 session:** ntdll reports `rtcs=0x153611C98`, and `0x153611C98 - 0x1534fd000` (the `[jit-pool]` base for libarm64ecfex) is rva `0x114c98`, which is `ResetToConsistentState`'s own rva in that build — `ResetToConsistentStateImpl` sat at `0x113e90`. So the wrapper is the function ntdll calls, and it was returning at the null-state guard before ever reaching the old dump site |

| `0009-exittox64-prefer-native-when-uninitialised.patch` | Stop turning a bitmap rejection into a guaranteed crash. Reaching `ios_thunk_reject` normally means "emulate", which is right for a genuine x64 target — but the same site is reached during `process_attach`'s DllMain walk, where no thread has a `CpuStateFrame`, so `enter_jit` reads an all-zero CPU area and executes `br x16` with `x16 = 0`: the `c0000005` at `pc=0` that survived ml1215–ml1219. Two conditions make a native branch the only sound answer, and the patch requires both: `x17` is a real code address — established either by actually following an FFS stub (`[sp+24] != 4`), or, when nothing was followed, by the slot value in use being a full address (`>= 0x100000`), since a bound IAT slot holds a resolved address and not an rva — and such a stub's `jmp` target is that image's native ARM64EC body *by construction*, since `.hexpthk` is the x64-visible face of native code, which is why ucrtbase reaches it through an exit thunk at all — and `DispatcherLoopTopEnterEC` is NULL, i.e. FEX has not initialised the thread so the emulation branch would dereference NULL. If FEX is live the bitmap keeps its authority; if the slot holds an unbound hint/name rva or `0xcc` filler, nothing changes. The second route matters because the alternative is not correct emulation but `br x16` with `x16 = 0` — given a guaranteed fatal fault, a resolved native address is the better branch on any accounting. ml1220 had only the first route and would have missed the case where the slot already held the native address, so nothing was left to follow. **Established this round:** `kernelbase!GetCommandLineA` is ordinal 340, rva `0x81330` in `.hexpthk`, bytes `48 8b c4 48 89 58 20 55 5d e9 be 34 fd ff`, a 14-byte fast-forward stub whose `rel32` `-0x36b42` lands on rva `0x4a7fc` in `.text` — the native ARM64EC body |

| `0012-hypervisor-leaves-honour-hidehypervisorbits.patch` | Gate the whole `0x40000000` leaf range on `HideHypervisorBit`, so `FEX_HIDEHYPERVISORBIT=1` hides the hypervisor *leaves* and not only `CPUID.1[31]`. Without it the option defeated itself: leaf 1 said "no hypervisor present" while `0x40000000` answered `eax = 0x40000001` with the signature `FEXIFEXIEMU`, and `0x40000001` answered `eax[3:0] = 2` = "the host architecture is AArch64". No real machine answers both ways, so the inconsistency was itself the fingerprint — and a more reliable one than the bit it was hiding, because emulator detection queries exactly these leaves. A protected title reaching an unambiguous "you are under FEX" verdict stops decrypting its own function prologues, which presents as a permanent `#UD` at a prologue whose file bytes are still ciphertext (Forza Horizon 6, RVA `0x537099C`, `[ud-decrypt] BYTES UNCHANGED`). With the option on, both leaves answer all zeros — the shape a real CPU gives an unimplemented leaf, and what `Function_Reserved` already returns. With the option off nothing changes, so nothing that relies on FEX's leaves is affected. This is a compatibility fix of the same kind as the hotpatch import thunks: the emulator stops volunteering that it is an emulator; nothing the guest checks is weakened or disabled |

A patch must apply on the current FEX pin. When the pin moves, rebase the
patches onto it (or drop a patch the new pin already covers).
